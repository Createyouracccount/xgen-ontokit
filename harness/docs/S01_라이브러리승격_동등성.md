# S01 — 검증된 경로의 라이브러리 승격: 동등성 증명 (2026-10-10)

L02 에서 검증된 경로(그래프 투영 → 질의 컴파일 → 병합)는 측정 하네스(`harness/`, 패키지 밖)에만 있었다.
이를 `src/ontokit` 으로 옮기고, 하네스가 라이브러리를 import 하게 바꿨다. **동작을 바꾸지 않는 이동**이므로
완료 조건은 "옮긴 코드로 다시 계산해도 L02 와 같다"이다. HOLDOUT 측정은 다시 열지 않았다.

## 1. 무엇을 옮겼나

| 라이브러리 | 원래 위치 | 내용 |
|---|---|---|
| `ontokit.graph` | `harness/graph.py`(`ontokit_graph`·`KLUE_MAP`·`_add_names`·`_tbox`), `harness/schema.py`(어휘·URI·`norm`) | 추출 결과 → RDF 투영. 관계 어휘는 KLUE-RE 라벨 12종 |
| `ontokit.query` | `harness/query.py`(`Compiler`·`run_plan`) | 계획 → SPARQL. 인메모리 `run(g, plan)` 추가(§3) |
| `ontokit.merge` | `harness/merge_eval.py`(병합 규칙), `harness/hybrid.py`(그래프 블록) | `graph_block`(판독 프롬프트) · `merge`(판독 답 ∪ 그래프) |
| `ontokit.planner` | `harness/planner.py`(프롬프트) | 질문 → 계획 프롬프트 · 엄격 파서(§7 이후 추가) |
| `ontokit.pipeline` | `harness/build_ontokit.py`(추출 구성) | 문서 → 추출 결과. `ontokit build` 와 하네스가 공유(§7) |
| `ontokit.backends.oxigraph` | (신규) | 내장 SPARQL 저장소 — 하네스의 Fuseki 대체(§6) |

하네스에 남긴 것: Wikidata 매핑(`harness/schema.py` — 정답 채점용), 오라클·위약 그래프, Fuseki 적재, 채점·통계.
하네스 모듈은 라이브러리 객체를 그대로 쓴다(사본 아님 — `tests/test_standalone.py::test_harness_uses_library_objects`).

## 2. 동등성 — 결과

| 검사 | 대상 | 결과 |
|---|---|---|
| ① 투영 트리플 집합(이동 전 코드 vs 라이브러리) | wiki2 r5 · wiki2 h2 · HOLDOUT r5 그래프 | 3/3 동일(정렬 N-Triples 해시 일치) |
| ② 측정 당시 Fuseki 적재본 vs 라이브러리 투영 | `g/r1/ontokit_r5` 181,105 · `g/r1/ontokit_h2` 242,291 · `g/H/ontokit_r5` 156,418 | 3/3 트리플 집합 동일(양쪽 차이 0) |
| ③ SPARQL 문자열(이동 전 vs 라이브러리) | EVAL 저장 계획 × 그래프 팔 4개 = 1,112 | 1,112/1,112 동일 |
| ④ merge_eval 재계산(라이브러리 경로, Fuseki) vs 저장 결과 — **문항 × 팔, 기록 전 필드** | `L2_eval_merge.json` MRG:ontokit_r5 · MRG:ontokit_h2 | 210/210 · 210/210 동일 |
| | `L2_eval_ctrl_merge.json` MRG:oracle · MRG:placebo2 | 68/68 · 68/68 동일 |
| ⑤ 양성 대조 — 개수 규칙을 끈 병합으로 ④ 반복 | MRG:ontokit_r5 | **9문항 다름**(전부 집계형 A) → 비교기가 차이를 잡는다 |

④ 의 집계는 L02 와 같다: MRG:ontokit_r5 − VLLM **+0.081 [+0.049, +0.115]**, 조회(L) 0.735 − 0.759 = −0.024,
양성 대조 MRG:oracle +0.699 [+0.599, +0.792], 음성 대조 MRG:placebo2 +0.023 [−0.024, +0.083]. ④ 에서 그래프 결과가
실제로 들어간 문항은 87(r5) · 147(h2) · 51(oracle) · 43(placebo2)으로, 모두 비어서 같은 비교가 아니다.

⑤ 에서 배운 것: 개수 규칙을 꺼도 **집계 Δ 는 +0.081 그대로**였다 — 9문항의 개수가 바뀌었지만 전후 모두 오답이었다.
즉 ① 집계 일치만으로는 동등성을 말할 수 없어 문항 단위 비교가 필요했고, ② **개수 규칙의 EVAL 점수 기여는 0** 이다
(L02 "집계는 이득 없음"과 일치. 규칙은 측정된 그대로 유지한다).

재현:
```
python -m harness.merge_eval r1 harness/bench/wiki2_bench.json harness/results/L2_eval_merge.json \
    --pairs HYB:ontokit_r5,HYB:ontokit_h2 --out /tmp/S01_eval_merge.json
python -m harness.equiv rows harness/results/L2_eval_merge.json /tmp/S01_eval_merge.json MRG:ontokit_r5,MRG:ontokit_h2
python -m harness.equiv graph r1 ontokit_r5 harness/data/r5/ontokit_raw.json harness/data/wiki2/docs.jsonl
```
(Fuseki `ontoharness` 데이터셋과 gitignore 된 `harness/data/` 가 필요하다.)

## 3. 측정 기록과 문서의 불일치 — 정정

L02 §1 과 인계 문서는 병합을 "벡터 상위 40청크로 판독기가 낸 답 ∪ 그래프 결과"라고 적었다. 코드(`merge_eval`)가 실제로
합친 것은 **HYB 팔의 판독 답** — 판독기가 청크 **와 그래프 블록**을 함께 보고 낸 답이다. 그래서 검증된 경로는 두 단계다:
① 판독 프롬프트에 그래프 블록(`ontokit.merge.graph_block`)을 넣고 ② 그 답에 그래프 결과를 합친다(`ontokit.merge.merge`).
블록 없이 ② 만 쓰는 조합은 측정되지 않았다. 수치는 바뀌지 않는다(같은 결과 파일의 해석 정정).

## 4. 측정하지 않은 것

- HOLDOUT-1: 재계산하지 않았다(사용 횟수 2/3 그대로). ① ② 의 HOLDOUT 그래프 비교는 그래프만 보고 벤치·답은 열지 않았다.
- HYB 판독(LLM)은 다시 돌리지 않았다. `graph_block` 은 이동 전 `hybrid.read` 의 블록과 문자열이 같음을
  경계 사례 5개(항목 0·1·150·151·1,000개)로만 확인했다.
- 계획기 프롬프트는 이후 `ontokit.planner.PROMPT` 로 옮겼다(이동 전과 문자열 동일, 1,506자). LLM 호출·복구 파서는 하네스에 남겼다.

## 5. 서버 없는 질의(A2) — 인메모리(rdflib) = Fuseki

같은 그래프·같은 계획을 Fuseki(`run_plan`, 측정 당시 적재본)와 인메모리(`ontokit.query.run`, 원자료에서 다시 투영)로 돌려
문항마다 답 노드(URI와 이름 목록)를 비교했다(`python -m harness.parity_mem`). 계획은 두 출처 — 벤치 정답 계획과 MERGE 가 실제로
쓴 LLM 저장 계획.

| 그래프(트리플) | 벤치 정답 계획 | LLM 저장 계획 | 결과가 비지 않은 문항 | 양쪽 실패 |
|---|---|---|---|---|
| ontokit_r5 (181,105) | 210/210 동일 | 210/210 동일 | 90 · 87 | 0 |
| ontokit_h2 (242,291) | 210/210 동일 | 210/210 동일 | 167 · 147 | 0 |
| oracle (36,162) | 210/210 동일 | 68/68 동일 | 210 · 51 | 0 |
| placebo2 (35,976) | 210/210 동일 | 68/68 동일 | 174 · 43 | 0 |

- 양성 대조: 같은 계획을 r5 그래프와 h2 그래프에 넣으면 210 중 141 문항이 다르다 — 비교기는 차이를 잡는다.
- 인메모리 질의 시간: 문항당 최대 0.1초(18만~24만 트리플).
- 인메모리는 GRAPH 절 없이, Fuseki 는 GRAPH <이름> 으로 감싼 같은 본문을 실행한다(`Compiler.compile(plan, graph=None)`).

## 6. Fuseki 제거 — 하네스 저장소를 Oxigraph(내장, 서버 없음)로

이유: Fuseki(TDB2)는 지운 트리플·compaction 세대를 회수하지 않아 디스크에 쌓인다(사내 기록 07-26: 살아 있는 3GB 가 20GB).
이 하네스의 `ontoharness` 데이터셋도 그래프 13개(1,411,188 트리플)에 **3.0GB** 를 쓰고 있었다(세대 디렉터리 1개·compaction 이력 없음 — 지우고 다시 실은 트리플이 회수되지 않은 것으로 추정, 원인은 따로 확인하지 않았다).

`harness.graph.store()` 를 `ontokit.backends.oxigraph.OxigraphStore`(디렉터리 `harness/data/graphs`, gitignore)로 바꾸고,
측정 그래프 13개를 원자료에서 다시 투영해 실었다(`python -m harness.graph load …`, 13개 45초).

| 확인 | 결과 |
|---|---|
| 그래프 13개 트리플 수 vs Fuseki | 13/13 같음(ontokit r1~r5·h2, oracle·placebo·placebo2 × EVAL·HOLDOUT, HOLDOUT ontokit_r5) |
| 인메모리 ↔ Oxigraph(§5 와 같은 방식) | 4개 그래프 × 계획 2종 문항별 전부 동일 |
| merge_eval(Oxigraph) vs 저장 결과 | MRG:ontokit_r5 210/210 · ontokit_h2 210/210 · oracle 68/68 · placebo2 68/68 동일, Δ +0.081 [+0.049, +0.115] |
| 계산 시간(같은 merge_eval) | Fuseki 2분 29초 → Oxigraph 2.2초 |

디스크 — 같은 13개 그래프를 지우고 다시 싣기를 반복:

| | Oxigraph |
|---|---|
| 1회 적재 | 389 MB |
| 2·3·4회(매번 13개 전부 교체) | 430 · 438 · 434 MB — 쌓이지 않는다(RocksDB 가 스스로 compaction) |
| `optimize()` 후 | 369 MB |
| 참고: 같은 데이터의 Fuseki | 3.0 GB |

Neo4j(LPG, `harness/parity.py`·`lpg.py`)는 여전히 graphstore 를 선택 의존으로 쓴다(Cypher 경로 라이브러리 승격은 다음 과제).

## 7. CLI(A3) — 새 venv 에서 build → query, 그리고 환경 민감도

`ontokit build` 와 하네스 빌드(`harness/build_ontokit.py`)는 같은 함수(`ontokit.pipeline.extract`)를 쓴다.
wiki2 앞 60문서, L02 추출 설정(관계 인코더 v13c + §STANDALONE 5 의 스위치)으로 비교했다.

| 빌드 | 환경 | 이동 전 하네스 빌드와 비교 |
|---|---|---|
| 새 코드(하네스) | 개발 환경 | 개체·관계·계층 동일 |
| 새 venv `ontokit build`, 개발 환경과 같은 버전 고정 | transformers 5.14.1 · torch 2.11.0 · kiwipiepy 0.23.2 | **그래프 트리플 집합 동일**(3,287) |
| 새 venv `ontokit build`, 최신 버전 | transformers 5.19.0 · torch 2.14.1 · kiwipiepy 0.24.0 | 개체 902→905, 하위 클래스 32→26, 트리플 3,287→3,275 |
| 위에서 kiwipiepy 만 0.24.0 | | 최신 버전과 그래프 동일 → **차이는 kiwipiepy 0.24** 에서 온다 |

torch·transformers 차이는 관계 신뢰도 점수 넷째 자리(0.9194→0.9193)만 바꾸고 그래프는 바꾸지 않았다.
→ L02 그래프를 재현하려면 kiwipiepy 0.23.2 가 필요하다. 0.24 가 더 나은지 나쁜지는 측정하지 않았다.

함께 발견한 것(이동과 무관, 기존 동작): `concepts.classes[].source_chunks` 의 **순서**가 파이썬 해시 시드에 따라 달라진다
(같은 코드·같은 환경, `PYTHONHASHSEED` 1 과 2 에서 33개 클래스). 그래프 투영은 이 필드를 쓰지 않아 그래프는 같다.

새 venv(macOS arm64, Python 3.13, 이 브랜치를 로컬 경로에서 `[korean,ner,owl]` 로 설치 — 태그 미푸시라 git 태그 설치는 못 했다):
- `ontokit build` → `ontokit query` 동작, 결과에 출처 문서(`docs`)가 붙는다
- `ontokit ask` 는 LLM 설정이 없으면 이유를 말하고 종료 코드 1
- 폴더 입력(.txt, 빈 파일 포함)·관계 가중치 없음: "관계 채널 꺼짐"을 알리고 타입·클래스만 만든다
- 측정 안 함: Linux·다른 Python 버전, git 태그 설치, NER 가중치를 처음 받는 깨끗한 HF 캐시
